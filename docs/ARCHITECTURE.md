# Архитектура: решения и обоснования

Документ фиксирует расхождения с исходным паспортом v1.0.0 и причины изменений.
Каждое решение — с ценой, чтобы его можно было осознанно откатить.

## Стек

| Что | Решение | Почему |
|---|---|---|
| Язык | C# 13, .NET 10 (LTS) | Единственный вариант, где COM/Shell-интеграция (OLE drag&drop, `SHGetFileInfo`, Корзина, диалог «Свойства») пишется за часы, а не за недели |
| UI | WPF | Виртуализация списков «из коробки», полная перерисовка стилей под DOS-вид, XAML вместо ручного Win32 |
| Сборка | self-contained, single-file, x64 | У пользователя не должно быть установленного .NET Desktop Runtime — в Windows 11 его нет |
| Сторонние библиотеки | **ноль** | Только BCL + P/Invoke к kernel32/user32/shell32 |

Цена решения: exe ~45–60 МБ. WPF не поддерживает NativeAOT, поэтому меньше не будет.
Альтернатива с exe на 4 МБ существует (NativeAOT + голый Win32), но означает написание
всего UI вручную.

## Отменённые решения паспорта

### SQLite — убран

Паспорт (п. 4.2, 4.3) хранит индекс и кэш метаданных в SQLite. Это NuGet-пакет плюс нативная
DLL, то есть прямое нарушение требования «без зависимостей». Функционально он тоже проигрывает:
наш индекс — плоский массив имён, и его сериализация в собственный бинарный формат читается
одним `File.ReadAllBytes` за миллисекунды, тогда как SQLite потребовал бы парсинга миллиона строк.

Заменено на: собственный бинарный формат индекса + `System.Text.Json` (встроен в BCL)
для настроек, сессий и шаблонов.

### Trie — заменён на плоский буфер имён

Паспорт (п. 8.1) оценивает Trie в 50–80 МБ на 1 млн имён. Для .NET это нереалистично: узел —
объект с заголовком в 24 байта плюс коллекция потомков, реальный расход 400 МБ – 1 ГБ при
заявленном требовании ОЗУ в 512 МБ (п. 11).

Более важно, что Trie **ищет только по префиксу**. Запрос `sofa` не найдёт `red_sofa_final.blend`,
хотя пользователь ожидает именно этого.

Заменено на: все имена встык в одном `char[]`, запись хранит смещение и длину
(см. `MftIndex.Entry`). Миллион имён ≈ 60 МБ, поиск подстроки — линейный скан
с `MemoryExtensions.Contains`, который в .NET векторизован. Ожидаемо десятки миллисекунд
на миллион записей; фактические цифры даст `tools/MftProbe`.

### Bloom filter — переставлен на другое множество

Паспорт (п. 8.2) строит фильтр над **именами файлов** и спрашивает у него «есть ли файл
с таким именем». В таком виде он бесполезен: фильтр Блума проверяет членство точного ключа,
а пользователь ищет подстроку — хеш от `sofa` и хеш от `red_sofa.blend` не связаны никак.
Чтобы покрыть подстроки, в фильтр пришлось бы класть все подстроки всех имён: для 1 млн имён
по 20 символов это ~200 млн ключей и, по формуле самого паспорта, около 240 МБ вместо
обещанного 1 МБ.

Сохранено с заменой множества: фильтр строится над **биграммами внутри каждого имени**
(`MftIndex.Signatures.cs`). Имя `red_sofa.blend` кладёт в свою 64-битную сигнатуру биграммы
`re, ed, d_, _s, so, of, fa, ...`; запрос `sofa` даёт `so, of, fa`. Проверка `(sig & q) == q`
отсеивает имя за одну операцию AND.

Математика фильтра Блума сохраняется полностью — односторонняя ошибка, те же оценки:

$$\text{fill} = 1 - e^{-n/m}, \qquad p = \text{fill}^{\,g}$$

где n — число биграмм имени, m = 64 бита, g — число биграмм запроса. Для имени в 20 символов
и запроса из 3 биграмм p ≈ 1,7 %, то есть 98 % записей не доходят до посимвольного сравнения.

Расход — 8 байт на файл (8 МБ на миллион), лежащих подряд, поэтому скан векторизуется через
`Vector<ulong>`: блок, в котором не прошла ни одна сигнатура, пропускается целиком.

Так устроены триграммные индексы в Google Code Search, Zoekt и `pg_trgm` в PostgreSQL.

Отдельный интерес представляет расхождение измеренной доли ложных срабатываний с расчётной:
формула предполагает равномерное хеширование, а биграммы реальных имён распределены крайне
неравномерно (`er`, `in`, `on` против `qz`). Бенчмарк печатает обе величины рядом.

### Красно-чёрное дерево фильтров — заменено на компиляцию выражений

Паспорт (п. 4.3, 8.3) применяет красно-чёрное дерево к дереву условий фильтра. В дереве
условий 5–15 узлов; балансировка окупается на тысячах вставок. Формулировка «O(log N) на
проверку одного файла» некорректна: проверка файла стоит O(числа условий) независимо от
структуры дерева.

Заменено на: AST условий компилируется в `Func<FileEntry, bool>` через
`System.Linq.Expressions`. Предикат становится нативным кодом, обход узлов на каждый файл
исчезает.

### Облачные REST API — отложены за пределы 1.0

Паспорт отводит 2 недели на OneDrive/Google Drive/Dropbox через REST. Это OAuth, регистрация
приложения, верификация у Google и неразрешимая задача хранения client secret в клиентском
приложении — отдельный проект, а не этап.

Заменено на: облачные папки показываются как закладки на локальные каталоги синхронизации
(`%USERPROFILE%\OneDrive` и аналоги). Работы — на вечер, покрывает реальный сценарий.

### Встроенный терминал — через ConPTY

Паспорт (п. 3.9) предлагает собственные `cd`, `dir`, `mkdir`, `del`. Windows предоставляет
**ConPTY** (`CreatePseudoConsole`), дающий настоящий хост-терминал с реальным cmd или
PowerShell внутри. Свои реализации команд не нужны.

## Ядро: индексация через MFT

Это главное архитектурное решение и главный технический риск проекта.

Паспорт (п. 3.4.2) строит индекс «рекурсивным обходом всех папок». На томе с миллионом
файлов это минуты работы и миллион обращений к файловой системе.

NTFS хранит запись о каждом файле тома в **Master File Table**, и её можно прочитать
последовательно одним потоком через `DeviceIoControl` с `FSCTL_ENUM_USN_DATA`. Именно так
Everything индексирует диск за секунды. Реализация — `tools/MftProbe/MftIndex.cs`.

Следствия, которые надо принять сразу:

1. **Нужны права администратора.** Открытие тома `\\.\C:` с `GENERIC_READ` доступно только
   привилегированному процессу. Приложение должно либо запрашивать elevation манифестом,
   либо иметь режим деградации на обычный обход каталогов для непривилегированного запуска.
2. **Только NTFS.** На exFAT и FAT32 (флешки, внешние диски) MFT нет — для них нужен
   резервный путь через `EnumerateFileSystemEntries`.
3. **`FileSystemWatcher` не нужен.** У USN Journal есть режим отслеживания изменений
   (`FSCTL_READ_USN_JOURNAL`), который не теряет события при переполнении буфера — а
   `FileSystemWatcher` на больших деревьях теряет.

## Blender: две поправки к паспорту

**Запуск файла.** Паспорт (п. 6.2) предлагает `blender.exe -b "файл.blend"`. Флаг `-b` — это
background-режим: Blender выполнит запуск без окна и сразу завершится. Для открытия по
двойному клику нужно `blender.exe "файл.blend"` без флагов.

**Превью — фича снимается с 1.0.** Паспорт (п. 6.1) рассчитывает на `IThumbnailProvider`;
Blender его в Windows не регистрирует, этот путь закрыт. Обходной путь — читать превью
из самого файла — проверен на реальной коллекции пользователя (34 файла) и оказался
нежизнеспособным:

| Факт | Следствие |
|---|---|
| 23 из 34 файлов сжаты zstd (сигнатура `28 B5 2F FD`) | заголовок недоступен без распаковки, а **в .NET нет встроенного zstd** (`System.IO.Compression` знает Deflate, GZip, Brotli, ZLib — но не Zstandard). Поддержка потребовала бы NuGet-пакета, то есть нарушения требования «ноль зависимостей» |
| ни в одном из 11 несжатых файлов нет блока `TEST` | превью физически отсутствует: опция «Save Preview Images» выключена, а она выключена по умолчанию |
| превью в `TEST` хранится как сырой RGBA (`width`, `height`, затем пиксели), не как PNG | поиск сигнатуры `89 50 4E 47` внутри `.blend` не найдёт ничего — искать нечего |

Решение для 1.0: собственная моноширинная иконка для `.blend`, консистентная с DOS-темой.
Вернуться к превью можно, если понадобится — но цена вопроса: зависимость от zstd плюс
требование к пользователю включить сохранение превью в настройках Blender.

## Порядок работ

Порядок этапов паспорта развёрнут: самый рискованный кусок идёт первым, чтобы провал
гипотезы обнаружился на второй неделе, а не на третий месяц.

1. **MFT-индекс и поиск** — `tools/MftProbe`, замер на реальном диске *(текущий этап)*
2. Сериализация индекса на диск + инкрементальное обновление через USN Journal
3. Оболочка WPF: список с виртуализацией, навигация, адресная строка
4. Вкладки, сессии, восстановление состояния
5. Файловые операции (копирование с прогрессом, конфликты имён, отмена, длинные пути)
6. Тема MS-DOS, режимы просмотра, иконки через `SHGetFileInfo`
7. Blender: шаблоны проектов, дублирование структуры, превью из `.blend`
8. Диски и статистика
9. Конструктор фильтров
